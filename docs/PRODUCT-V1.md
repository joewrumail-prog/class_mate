# classmate 产品定义 v1.0

> 来源：2026-07-06 三轮产品问答收敛。本文档是当前唯一权威定义，此前文档与本文冲突处以本文为准（修订清单见 §8）。

## 1. 一句话定义

**classmate 是大学生的时间×精力操作系统**：吃进课表、Canvas deadline、健身计划和社团安排，自动生成并动态调整从一周到每天的计划，用"系统"人格在合适的时机派任务、在劳累的时候踩刹车；附着一个审核制的校园公告空间（Room），解决招新、活动和找搭子。

不做的事（刻意）：不做站内聊天、不做算法匹配社交、不写外部日历、MVP 不接邮件。

## 2. 解决什么问题

大学生每天开工前要开 N 个平台（邮件、Canvas、学校各种网页）才能拼出"我今天该干什么"；有健身习惯或社团活动的人还要手动权衡 ddl、时间、精力。classmate 把这个每日决策外包掉：**打开即知道现在该干什么、为什么是它、今天还剩多少精力预算**。

目标用户：被日程和学校信息碎片折磨的所有学生（主战场），以及想在百人 lecture 里认识同学的学生（Room 承接）。

## 3. 支柱一：调度系统

### 3.1 数据输入（MVP 三源）

| 源 | 方式 | 备注 |
|---|---|---|
| 课表 | 手动录入 / ICS / 截图解析 | 含上课校区——通勤计算必需（隐私处理见 §7） |
| Canvas | 用户自己生成 API token 授权 | 作业、ddl、课程公告 |
| 自建承诺 | 用户录入 | 健身计划（频次+时长）、社团、打工、自定长期目标 |

邮件与学校网页聚合 = P2，且邮件默认端侧处理，全文不进服务器（隐私红线）。

### 3.2 调度算法 v0（规则引擎，无 ML）

硬约束先占位：课程块 + 校区间通勤缓冲（校区对通勤矩阵 + 校车班次冗余）。
软约束填充：每个任务有预估耗时和强度，按"精力预算"填入空档，日填充上限 80%，保留弹性。
压力分 = Σ(未完成任务耗时 × 强度) / 距 ddl 天数——分数驱动一周内的前置搬运（ddl 密集周提前一周分摊）。
重排触发器：任务超时未完成、新 ddl 进入、精力自报低值、用户手动拖动 block。重排只动未来，不改历史。

### 3.3 精力评估 v0（规则 + 自报，无穿戴设备）

基线 = 睡眠窗口长度（用户设定作息）+ 当日课程密度扣减。
自报 = 每日一次轻量输入（状态 1–5，一次点击），作为当日预算乘数。
自报 ≤2 触发保护模式：自动砍掉当日低优先级 block，只留 ddl 临近项 + 恢复建议。
连续 3 天低自报 → 系统降低整周填充率，并在周复盘中指出。
数据沉淀：自报序列 + 完成率是后续个性化（P2 的真·算法）的训练数据，从 Day 1 就存。

### 3.4 系统人格（核心差异化，不是游戏化）

原则：像网文主角的"系统"——**发任务、给反馈、守护长期目标**，没有 XP、没有徽章、没有排行榜。

- 任务发布：时机触发而非清单展示。早晨给"今日主线 + 支线"；空档开始时推"当前最优任务"（含理由：耗时、精力匹配度、ddl 压力）
- 劳累干预：压力分高或自报低时主动降载："这周超载了，我把周四的健身移到周六，CS336 提前到今晚精力峰值"
- 长期目标叙事：周复盘讲进度故事（"健身坚持第 5 周，长期目标完成 34%"），黏性来自被持续见证，不是被打分
- 语气：冷静、可靠、略少话。像系统，不像客服

系统人格名待定（候选：Atlas / Sage / Pace / Dean，建议 Atlas），app 名保持 classmate。

### 3.5 内置日历

自带 block 式日历（系统排的 block + 用户手动 block 共存，拖动即重排）。不读写 Apple/Google 日历——化简权限、避免污染用户已有日历，代价是用户需要以 classmate 为主视图，这正是"常驻"的产品意图。

## 4. 支柱二：Room（审核制校园空间）

### 4.1 形态

按学校一个 Room（后续可按课程/社团分区）。贴类型四种：**社团招新、活动介绍、party 公告、个人搭子寻找**。无聊天、无评论（P1 再议），联系方式走"请求—同意"交换，不公开挂出。

### 4.2 审核流水线（发布前审核）

```
提交 → OpenClaw agent 初筛（分类 + 版规检查 + 置信度）
  ├─ 干净且高置信 → 自动过
  ├─ 边界/低置信 → 人工队列（Joe 复核）
  └─ 明确违规 → 自动拒 + 给理由
```

版规 v0：允许四类贴型内；禁止 dating/hookup 向、未报备商业广告、匿名攻击、违法内容；二手/转租暂不开放（需要单独版面时再议）。招新季 SLA <24h。OpenClaw 初筛只处理贴文内容本身，不接触用户账号数据（见 §7 模型路由）。

## 5. 平台路线

**Web 先行（MVP，9/1）**：登录、三源导入、周计划+日视图、自报、Room。全流程跑通。
**Mac 第二**：menu bar 常驻 + 通知——"开工前决定干什么"的主场景。
**iOS 第三**：widget + 锁屏——全天视线内。

三端 SwiftUI 共享（Mac/iOS），web 独立。账号一套（.edu 邮箱验证，沿用原方案）。

## 6. 成功指标

北极星：**每日打开并领取当日计划的用户比例**（daily plan engagement）。
辅助：计划完成率（系统排的 block 被执行的比例，>50% 说明排得准）、自报参与率、周留存、Room 贴的联系请求转化。
渗透率指标降级为 Room 层指标，不再是全局北极星。

## 7. 隐私修订要点（v0.2 重写依据）

1. **地点政策反转**：旧文档"不采集上课地点"作废——通勤计算需要校区级位置。新原则：**位置数据只服务于用户本人的调度，永不出现在 Room 或任何他人可见面**。采集粒度到校区/楼，不到教室
2. 联系方式 = 最敏感 PII：请求—同意交换，拒绝不通知理由，可撤回
3. Canvas token 加密存储，只拉作业/公告，可一键断开并删除衍生数据
4. 邮件红线：P2 接入时端侧处理，服务器不见全文
5. 精力自报属于健康相邻数据：不进任何分析平台、不参与 Room、导出/删除随账号
6. 模型路由（沿用三档）：调度和用户数据只走不训练的 API（Anthropic 档）或本地规则；OpenClaw 初筛 Room 贴文可用便宜模型（贴文本来就是要公开的内容）；DeepSeek 托管 API 永不碰用户级数据

## 9. 待定问题

系统人格名最终拍板；调度算法的通勤矩阵数据来源（Rutgers 校车 GTFS 有公开数据，需工程验证）；Room 是否要课程级分区还是学校级一个（MVP 建议学校级一个，密度优先）；商业化路径（暂缓，先留存）；健身计划的粒度（自由文本 vs 结构化模板）。
