# classmate Web MVP 设计需求简报（DESIGN-BRIEF v1）

> 读者：设计侧（视觉 / 交互）。你们不需要读代码，也不需要读数据库 schema——本文已把开发 Spec（DEV-SPEC-V1 §7 API 面、§10 验收标准）翻译成界面需求。
> 每个界面一节，格式固定：目的 / 核心元素 / 数据契约（这块屏幕上会出现哪些数据，用产品语言描述，括号里标注 Spec §1 的来源表，仅供对照，不必深究）/ 关键交互 / 空态与错误态 / 对应验收条目（指 DEV-SPEC §10 的编号，设计稿评审时按编号对账）。
> 平台：Web 先行（桌面浏览器为主，移动浏览器必须可用），9/1 上线。Mac / iOS 不在本期。

## 0. 全局原则（先读这节，再看单屏）

### 0.1 系统人格「Atlas」语气规范（源自 Spec §8）

产品里所有"系统说的话"（晨间简报、空档推送、保护模式提示、周复盘、shed 理由）都出自同一个人格 Atlas。文案由模板引擎生成（不是每次现写），所以设计稿里的示意文案请遵守同一套规则，否则开发会替换掉：

- **冷静、克制、略少话**。像网文里的"系统"，不像客服，更不像营销号。
- **每句话给理由**。派任务必须带"为什么是它"（耗时 / 精力匹配 / ddl 压力），砍任务必须带"为什么砍"。
- **禁止感叹号，禁止"加油""你可以的"类打气话。**
- **禁止负债式催促**："你还有 N 项未完成"这类句式不允许出现。替代句式是"主线在等一步：X"。
- 干预示例（可直接当占位文案风格参考）："这周超载了。周四的健身移到周六，CS336 提前到今晚精力峰值。"
- 视觉含义：Atlas 的消息应有统一的、可识别的容器样式（区别于普通 UI 文本），但**不建议做拟人头像 / 表情**——它是系统，不是吉祥物（最终视觉方向见 §14 开放问题）。

### 0.2 隐私红线（哪些数据永远不出现在"他人可见面"）

"他人可见面" = Room 贴、天道榜、任何别的用户能看到你的地方。以下数据只允许出现在用户本人的私有界面上：

| 数据 | 说明 |
|---|---|
| 课表与位置 | 上课时间、教学楼、校区、通勤路线——只服务本人调度，**任何形态都不进 Room / 榜单**（产品定义 §7 明确反转过：采集校区级位置，但仅自用） |
| 精力自报 / 睡眠 / 心情 | 属于健康相邻数据。不出现在他人面，也不出现在任何分享卡默认内容里 |
| 联系方式（微信 / QQ / iMessage / IG / 邮箱） | 最敏感 PII。**永不公开挂出**，只走"请求→同意"交换流（见 §10 联系交换屏）；被拒绝方不会看到拒绝理由 |
| Canvas 数据 | 作业、成绩相关信息只进本人计划 |
| 真实姓名与身份 | 天道榜只显示用户自设的化名（alias），且用户可整体退出榜单 |

设计上的推论：任何"分享 / 截图友好"的设计（比如完成小票卡）默认内容只含计数与状态，不含课程名、地点、自报值。另外账号删除入口（设置页内，本期低保真即可）要能承载"删号 = 全部数据即刻销毁"的语义（验收 12）——按钮语气要严肃，二次确认要说清后果。

### 0.3 系统人格 ≠ 客服，也 ≠ 游戏化

- Atlas 发任务、给反馈、守护长期目标。它**不道歉、不卖萌、不感谢你的耐心等待**。
- XP / 等级 / 天道榜是独立的激励层（已有一版线上 UI，见 §12），Atlas 的话术里不吆喝 XP（"完成可得 20XP！"是禁止的）；XP 结算以安静的方式出现（pill / toast）。
- 加载、报错等系统状态文案可以沿用 Atlas 语气（"解析中。通常不超过一分钟。"），但纯技术性报错（500）用中性文案即可，不必强行人格化。

### 0.4 通用视觉语言（跨屏复用，请先定义为组件）

- **Block（计划块）**：全产品最核心的原子。五种类型：课程 / 通勤 / 任务 / 承诺（健身、社团等）/ 缓冲。六种状态：计划中 / 已完成 / 已错过 / 已卸载（shed）/ 已移动 / 进行中（当前时刻所在块）。类型用色相区分，状态用明度 / 纹理 / 描边区分，**shed 态必须一眼可辨且带"可撤销"入口**。
- **Pending 徽标**：Room 贴、联系请求、导入解析等多处需要"等待中"态，请统一。
- **精力预算条**：今日容量（0–120%）的展示组件，Today 与 Checkin 复用。
- 埋点对设计无感知负担，唯一要求：北极星是"每日打开并领取计划"，所以 **Today 首屏必须让"今天的计划"零点击可见**。

## 1. 登录（.edu 邮箱 Magic Link）

**目的**：用学校邮箱换一封登录链接邮件。无密码。

**核心元素**：产品名 + 一句话价值主张（落地页钩子："导入课表，看你这周还剩多少真实空闲"）；单个邮箱输入框；单个 CTA（"发送登录链接"）；发送成功态（"链接已发往 xxx@rutgers.edu，10 分钟内有效"之类）。

**数据契约**：只有邮箱一个输入。后端校验邮箱域名是否在学校白名单里（schools.edu_domains，MVP 只有 Rutgers：rutgers.edu / scarletmail.rutgers.edu）。

**关键交互**：
- 提交后按钮进入 loading → 成功态整屏切换为"去查收邮件"，附"重新发送"（带 60s 倒计时防连点）。
- **安全要求（影响文案）**：成功文案必须与"该邮箱是否已注册"无关——新老用户看到完全相同的成功屏，不允许出现"欢迎回来"/"账号不存在"。

**空态与错误态**：
- 非白名单域名 → 明确拒绝："目前仅支持 Rutgers 邮箱（@rutgers.edu / @scarletmail.rutgers.edu）"，可附"想让你的学校接入？"轻量登记入口（可选）。
- 邮件服务不可用（服务端 503）→ "登录邮件暂时发不出去，请稍后再试"，不暴露技术细节。
- 邮箱格式错误 → 前端即时校验。

**对应验收**：§10-1（白名单注册 → 魔法链接登录，非白名单被拒）。

## 2. Onboarding（目标画像 + 作息设定）

**目的**：首次登录后 3 步内完成：我是谁 → 我的目标 → 我的作息。产出直接喂给 Quest 编译器和精力模块。

**核心元素**：
1. 基本信息：显示名、专业、毕业年份。
2. **目标画像（archetype）单选卡**：3–5 张大卡（方向示例：冲学业 / 找实习求职 / 社团与社交 / 探索未定——最终文案与数量待产品定稿，设计按 4 张做弹性布局）。
3. **作息设定**：睡眠起止时间（双滑块或时间选择器）+ 时区（默认美东，可改）。要传达"这决定你的精力基线"，不是无关紧要的资料项。
4. 完成后的**编译过渡态**：系统正在根据你的画像生成任务线（可能数秒到数十秒），需要一个 Atlas 风格的等待屏；失败时自动降级为默认任务线，用户无感知阻塞。

**数据契约**：显示名 / 专业 / 毕业年份 / 目标画像（users.display_name, major, grad_year, goal_archetype）；睡眠窗口与时区（users.sleep_start / sleep_end / timezone）。

**关键交互**：分步向导，可回退；archetype 选中即预览一句"这条线会带你做什么"（来自骨架文案）；全部步骤可跳过除 archetype 外（无 archetype 无法编译任务线）。后续可在设置中更换 archetype → 触发重新编译（同一个过渡态复用）。

**空态与错误态**：编译超时 / 失败 → 不报错，落到默认线并提示"任务线先按通用模板生成，稍后会更贴合你"；表单校验常规处理。

**对应验收**：§10-6 前半（选 archetype → quest 线生成）。

## 3. 统一导入窗（上传 → 解析中 → 确认改错）

**目的**：用户扔进来任何课表载体（截图 / ICS / 手填兜底），90 秒内变成日历上的课程块 + 自动通勤块。这是新用户的 aha 时刻，全产品体验优先级最高的流程。

**核心元素**：
1. **上传态**：大拖放区（支持截图粘贴、文件选择），说明支持的格式；手动录入入口作为兜底并列。
2. **解析中态**：进度指示（前端轮询解析状态），Atlas 语气占位文案；预期 <60s，需设计 30s 后的"还在处理"缓释文案。
3. **确认改错屏（重中之重）**：解析结果按课程逐行列出——课程代码、名称、上课时间（星期 + 起止）、教学楼、校区、教师。**置信度低的字段高亮**（黄色底之类），点击任一字段行内编辑；支持整行删除与手动补一行。底部单个"确认导入"CTA。

**数据契约**：导入记录：识别出的类型、解析结果、置信度、状态（imports.detected_type / parse_json / confidence / status）；确认后生成的课程归属（user_sections）与课程目录信息：代码、名称、时间、教学楼、校区（catalog 课程目录三表，Spec §1 courses / sections / section_meetings）。

**关键交互**：确认后跳转 Today，新生成的课程块 + 通勤块以入场动效标示"这些是刚导入的"；确认屏的编辑操作要快（行内、无弹窗嵌套）。

**空态与错误态**：
- 无法识别文件类型 → 引导换截图或走手动录入。
- 解析失败 / 超时 → "没读出来。换一张更清晰的截图，或手动录入"，保留原文件重试按钮。
- 解析出 0 门课 → 视为失败态处理。
- 整体置信度低 → 确认屏顶部横幅提示"请重点核对高亮字段"。

**对应验收**：§10-2（截图 → 解析 → 确认改错 → 日历出现课程块 + 通勤块，全程 <90s）。

## 4. Canvas 连接

**目的**：用户粘贴自己生成的 Canvas API token，作业 / ddl 自动流入计划。

**核心元素**：
- 未连接态：说明"连接后作业自动进计划"；**分步图文引导**（去 Canvas 设置 → 生成 token → 粘回来），这是全流程摩擦最大的一步，引导质量决定转化。token 粘贴框 + 连接 CTA。
- 已连接态：连接状态、上次同步时间；**断开连接**按钮（红色系），断开 = 同时删除由 Canvas 衍生的所有数据，需要二次确认并说清。
- 隐私说明（一句话级别）：token 加密存储，只读作业与公告。

**数据契约**：连接状态与上次同步时间（canvas_links.status / last_sync_at）；同步进来的作业以 deadline 形态出现在计划里（deadline_items），本屏可给最近同步的作业数量摘要。

**关键交互**：粘贴 token → 即时校验（无效 token 当场报错，不入库）；连接成功要管理预期："首次同步最长 24 小时内完成，作业会自动排进你的计划"。

**空态与错误态**：token 无效 / 权限不足 → 行内错误 + 重新引导；同步失败态（已连接但上次同步失败）→ 状态点变黄 + "重试"。

**对应验收**：§10-3（token 粘贴 → 24h 内作业进计划）。

## 5. Today 日视图（核心主屏）

**目的**：打开即知道——现在该干什么、为什么是它、今天还剩多少精力。北极星指标（每日领取计划）就发生在这一屏，"今天的计划"必须零点击可见。

**核心元素**：
1. **单日 block 日历**（纵向时间轴）：五类块 × 六种状态（见 §0.4）；当前时刻线；通勤块视觉上明显"薄"于课程块。
2. **精力预算条**：今日容量百分比 + 已排负载占比。
3. **当前最优任务卡**（Atlas 推送的"空档开始"卡）：任务名、预计耗时、为什么是它（精力匹配 / ddl 压力），主按钮"开始"，次按钮"换一个 / 跳过"。仅在空档 >45min 且有候选任务时出现。
4. **块详情展开（reason 展开）**：点任意块展开抽屉——这个块为什么在这里（触发信号 + 安排效果两段模板文案，如"CS336 作业周四截止，压力分高 → 提前到今晚精力峰值"）；操作：标记完成 / 标记错过 / 移动。
5. **shed（被卸载）块**：保护模式或重排砍掉的块不消失，以压暗 + 标签形态留在原位或收进"今日已卸载"折叠区，**每个都带撤销**。
6. Atlas 消息入口（inbox）：晨间简报等落在这里，导航上有未读点。

**数据契约**：当日计划与容量（plans.date / capacity_pct / state）；每个块：类型、起止、强度、原因两段、状态、卸载理由（plan_blocks.kind / start_min / end_min / intensity / reason_signal / reason_effect / status / shed_reason）；块背后的课程 / 作业 / 承诺名称来自各自来源表。

**关键交互**：打开 Today = "领取"计划（状态从已生成→已查看，用户无感知，但设计上可用一个轻微的"今日计划已就绪"入场时刻强化仪式感）；完成块的反馈要轻（勾选动效 + 安静的 XP pill，不弹窗）；手动加块入口（+）。

**空态与错误态**：
- 未导入课表 → 全屏引导去导入窗（这是导入的主要流量来源）。
- 有课表但当日无任务 → "今天没有排任务。空档是你的。"（Atlas 语气,不填鸭）。
- 保护模式激活日 → 顶部持久横幅（见 §7）。
- 计划生成失败 → 显示裸课表块 + "计划稍后重试"。

**对应验收**：§10-2（导入后块出现在此屏）、§10-4（保护模式砍块可撤销）、§10-5（拖动重排联动，此屏与周视图共用）。

## 6. 周视图（拖动重排 + 受影响块高亮）

**目的**：一周全貌 + 手动调整的主战场。看 ddl 密度、把系统排的块拖到自己想要的位置。

**核心元素**：7 天 × 时间轴网格；块的视觉语言与 Today 完全一致（同组件，密度更高）；每日头部小型负载指示（当日容量利用率）；ddl 标记（截止日在时间轴上的锚点）。

**数据契约**：七天的计划与块（同 §5：plans + plan_blocks），外加各任务的截止时间（deadline_items.due_at）用于 ddl 锚点。

**关键交互（本屏灵魂）**：
- **拖动一个块 → 系统联动重排未来的块 → 所有被牵连移动的块短暂高亮**（呼吸一次的强调色），让用户看见"我动了一个，系统帮我理顺了后面的"。重排只动未来，历史不变——过去的天在视觉上应显著"封存"（压暗、不可拖）。
- 拖动约束：课程块与通勤块不可拖（硬块），拖动悬停时非法落点（与硬块冲突）要有明确拒绝反馈。
- 拖动结束前显示影子落点；重排计算期间被影响区域可给 200–500ms 的"计算中"微状态。

**空态与错误态**：未导入课表 → 引导导入；重排失败 → 块弹回原位 + toast 说明。

**对应验收**：§10-5（拖动 → 联动重排 → 受影响块高亮）。

## 7. Checkin（一击自报 + 保护模式）

**目的**：每天一次、一次点击级别的精力自报。它直接乘进当日容量，是全产品数据飞轮的起点，摩擦必须无限趋近于零。

**核心元素**：
1. **能量 1–5 单选**（大按钮，一排五个，点击即提交——不要"提交"二次确认）。
2. 可选补充（默认折叠）：昨晚睡了几小时（数值）、心情 1–5。
3. 提交后反馈：今日容量变化的即时可视化（精力预算条动一下）。
4. **保护模式提示（energy ≤2 时触发）**：Atlas 全宽卡片——"今天降载。我卸掉了 N 个低优先级块，只留下临近截止的。"附被卸载块列表，**每项带撤销**，整体带"全部恢复"。
5. 入口形态：Today 顶部的常驻轻量条（未填时），填完收起为小徽标；晨间简报内也含同一入口。

**数据契约**：当日自报：能量、睡眠时长、心情（checkins.energy / sleep_h / mood，一日一行）；保护模式砍掉的块（plan_blocks.status=shed + shed_reason）。

**关键交互**：点 1–5 即提交即生效（计划当场重排）；当日可修改（再点一次别的值 = 覆盖）；连续 3 天低自报时周复盘会提及（设计周复盘卡时预留该段落位）。

**空态与错误态**：已提交态显示今日值 + "点按可修改"；提交失败 → 按钮回弹 + 重试。保护模式卡在撤销后要优雅退场（不留尸体横幅）。

**对应验收**：§10-4（一击提交；energy=1 触发保护模式且被砍块可撤销）。

## 8. Quest 线与晨间简报（主线 / 支线卡）

**目的**：把 archetype 编译出的长期任务线呈现为"主线 / 支线"，并在每天早晨以简报形式派发当日任务。这是"系统人格"的叙事主场。

**核心元素**：
1. **任务线（quest line）总览**：四种线型——主线 / 支线 / 探索 / 社交，每条线是一个章节化的进度容器（章节名 + 线内进度）。
2. **Quest 卡**：标题、预计耗时、时间窗、XP 值、状态（未开始 / 进行中 / 已完成）。两个关键可供性：
   - **"为什么做这个"（why）可展开**：一段 Atlas 语气的理由。
   - **事实来源可点**：每个 quest 引用的校园事实（讲座、截止日、招聘会等）带来源链接（chip 形态，点击外跳原始 URL）。这是反幻觉的产品承诺，视觉上要可信、可见。
3. **晨间简报（07:30 本地时间）**：inbox 里的一封结构化消息——今日主线一步 + 支线一步 + （最多一条）机会侦察（"今天 14:00–16:00 你有空档，Room 里有一场 XX 讲座对你的求职线有用"）。简报同时是当日 checkin 的入口。
4. 换 archetype / 手动重编译入口（低频，放线总览的溢出菜单）。

**数据契约**：任务线：类型、标题、章节、状态（quest_lines.type / title / chapter / status）；单个 quest：标题、理由、事实引用、时间窗、耗时、XP、状态（quests.title / why / fact_ref / window_start / window_end / est_minutes / xp / status）；事实条目的标题与来源链接（fact_entries.title / source_url）。

**关键交互**：完成 quest → 线内进度推进动效 + 安静 XP 结算；why 展开是单击、无加载；fact 链接新开标签页。简报已读 / 未读状态。

**空态与错误态**：编译中（onboarding 后首次）→ 占位骨架卡；编译降级 → 显示默认线，无错误感；某条线全部完成 → 章节完结卡（叙事时刻，值得设计）。

**对应验收**：§10-6（每个 quest 的 why 可展开且 fact 来源可点）。

## 9. Room（审核制校园空间）

**目的**：一校一 Room 的公告空间。四种贴：社团招新 / 活动介绍 / party 公告 / 找搭子。无聊天、无评论、无点赞——它是公告栏，不是社交流。

**核心元素**：
1. **贴列表**：类型筛选 tab（四类 + 全部）；贴卡 = 类型徽标 + 标题 + 正文摘要 + 发布者显示名 + 有效期；活动贴额外带时间 / 地点 / "现场扫码得 XP"标记。
2. **发贴流**：选类型（四选一，各带一句说明与示例）→ 标题 + 正文 → 提交 → **进入 pending 态**。
3. **Pending 态（重要）**：提交成功后自己的贴以"审核中"徽标出现在"我的贴"里（其他人看不到）；审核通过 → 正常进列表；被拒 → 贴上出现拒绝理由（模板文案），可编辑重投。招新季审核 SLA <24h，pending 文案照此管理预期。
4. 贴卡上的主 CTA：**"请求联系"**（进入 §10 的交换流）。发布者视角则显示收到的请求数。

**数据契约**：贴：类型、标题、正文、状态（审核中 / 已通过 / 已拒绝）、过期时间（room_posts.type / title / body / status / expires_at）；发布者显示名（users.display_name）；活动贴关联的活动时间 / 地点 / XP（events.starts_at / venue / xp）。**注意：贴卡上没有任何联系方式字段——这是刻意的。**

**关键交互**：发贴表单要短（两个字段 + 类型）；过期贴自动从默认列表消失（可在"我的贴"看历史）；违规贴的拒绝理由要具体到版规条目（模板给），语气中性不羞辱。

**空态与错误态**：列表空 → "还没有贴。发第一张？"；单类型空 → 类型说明 + 发贴引导；提交失败 → 保留草稿。

**对应验收**：§10-7（发贴默认 pending，审核三分支全通）、§10-10 部分（活动贴承载扫码打卡入口）。

## 10. 联系交换（请求 / 接受 / 撤回三态）

**目的**：联系方式是最敏感 PII，全产品唯一的传播路径是"我请求 → 你同意 → 互见"。这一屏（实际是一组流程 + 一个管理页）承载该闭环。

**核心元素**：
1. **我的联系方式管理**：五种类型（微信 / QQ / iMessage / Instagram / 邮箱）各一个可填槽位。首次发起或接受请求时，若一个都没填 → 先引导填写（否则同意了对方也看不到东西）。
2. **发起请求**（从 Room 贴卡进入）：确认弹层说明"对方同意后，你们将互相看到对方选择公开的联系方式"。
3. **请求收件箱**：收到的请求（pending）→ 接受 / 拒绝两按钮。**拒绝无需理由、对方不会收到拒绝通知**（隐私要求，文案上要向拒绝者说明这点，降低拒绝的心理成本）。
4. **已连接列表**：双方 handle 卡（图标 + 可复制的值）；每条带**撤回**——撤回后双方互相不可见，且对方列表里静默消失。
5. 已发出请求列表（pending / 已接受；被拒绝的请求显示为一直 pending 或安静消失，不显示"被拒绝"）。

**数据契约**：我的联系方式：类型 + 值（contact_handles.kind / value_enc——加密存储，只有交换成功的双方可见解密值）；请求：来自谁、指向谁、关联哪张贴、状态四态（contact_requests.status：pending / accepted / declined / revoked）。同一对用户只能存在一个请求（不可反复骚扰性重发）。

**关键交互**：接受 → 立即展示对方 handle（这是回报时刻，可以有一点庆祝感，但克制）；撤回需二次确认（"对方将无法再看到你的联系方式"）；复制 handle 一键完成。

**空态与错误态**：收件箱空 → 简单占位；未填任何 handle 却尝试接受 → 阻断并引导补填；重复请求同一人 → 按钮置灰显示"已请求"。

**对应验收**：§10-8（请求 → 接受 → 双方可见 → 撤回后不可见，完整闭环）。

## 11. Seat Watch（蹲位提醒 + Paywall + Stripe）

**目的**：盯 Rutgers 满员课程的开位。免费 2 门，第 3 门起付费解锁（$4.99 / 学期，一次性支付）。全产品唯一的商业化界面。

**核心元素**：
1. **课程搜索**：按课程代码 / 名称搜索，结果显示 section 粒度——课程代码、section 号（index）、校区、教师、当前开 / 满状态。满员 section 带"Watch"按钮（这是本功能的目标对象）。
2. **Watch 列表**：每条 = 课程 + section 号 + 校区 + 教师 + 状态徽标（监控中 / 已开位 / 又满了）+ 最近一次见到开位的时间；删除（停止监控）。
3. **开位时刻**：已开位条目置顶 + 强状态色 + "去 WebReg 抢"外链；同时用户会收到邮件（<6 分钟送达），界面与邮件视觉同源。
4. **Paywall**：添加第 3 门时弹出——已用 2/2 的额度可视化 + "$4.99 本学期无限 Watch" + 单 CTA 去支付。**不做黑暗模式**：额度用量在列表页常驻可见，paywall 不装作错误。
5. 支付走 Stripe Checkout（跳转 Stripe 托管页），需要设计：跳转前的确认态、支付成功回来的解锁庆祝态、支付取消返回态。

**数据契约**：搜索结果与状态（catalog 课程目录：课程代码 / 名称、section 的 index 号 / 校区 / 教师 / 是否开放 / 最近开放时间，Spec §1 sections）；我的 watch 列表（seat_watches.status）；开 / 关位历史事件（seat_events.kind / observed_at，可选展示"过去 24h 开过 2 次"）；付费状态（subscriptions.plan=seatwatch_unlimited / status）。

**关键交互**：添加 watch 一键完成；已购用户不再见任何额度 UI；开位通知点进来直达对应条目。

**空态与错误态**：无 watch → 解释这是什么 + 搜索框引导；搜索无结果 → 检查课程代码格式提示；支付失败 / 取消 → 回到 paywall，额度不变，无惩罚性文案。

**对应验收**：§10-9（第 3 门被拦截；$4.99 支付解锁；开位邮件 <6min）。

## 12. 天道榜 + XP

**目的**：等级 / XP / 排行榜激励层。注意：**现有产品已有一版 system UI（等级、XP pill、quest 卡等）在线上运行且本期冻结**——本屏设计以"延展现有视觉"为前提，不推倒重做。

**核心元素**：
1. **我的 XP 面板**：当前等级、到下一级的进度、下一级解锁的 perk；XP 来源明细（完成块 / 完成 quest / 活动打卡）。
2. **天道榜**：**只显示 Top 10** + 我自己的在榜状态（"你在榜上" / "你不在 Top 10"），**不显示我的具体名次，也不显示 10 名以外任何人**（隐私验收硬要求）。榜上显示的是化名（alias），不是真名。
3. **化名与退出**：设置自己的榜单化名；一键退出榜单（opt-out 后自己完全不出现）。
4. **活动打卡的 XP 规则可视化**：扫活动二维码得 XP；重复扫码无效（幂等）；**每周活动 XP 有 30% 上限**——达到上限后打卡成功但不再加 XP，界面要如实显示"本周活动 XP 已达上限"，不能让用户以为打卡失败。

**数据契约**：等级 / XP / 化名 / 是否上榜（users.level / xp / leaderboard_alias / leaderboard_opt_in）；XP 流水与原因（xp_ledger.delta / reason）；等级表与 perk（levels.xp_required / perk_key）；活动打卡记录（event_checkins，一人一活动一次）。

**关键交互**：升级时刻（现有 LevelUpModal 组件已存在，沿用）；打卡扫码流程：活动贴 → 现场二维码 → 扫码落地页（成功 / 已打过 / XP 上限三种结果态）。

**空态与错误态**：榜单不足 10 人 → 显示实际人数，不留空坑；opt-out 状态下看榜 → 正常看 Top 10，附"你已退出榜单"说明；重复扫码 → "已记录过，XP 只结算一次"（中性，不当作弊指控）。

**对应验收**：§10-10（重复扫码幂等、XP 只结算一次、周 30% 上限后不再累计）、§10-11（只显示 Top 10 与本人在榜状态）。

## 13. 管理后台（审核队列，低保真即可）

**目的**：内部工具，Joe 一个人用。功能完整 > 视觉打磨，线框级交付即可。

**核心元素**：
1. **人工审核队列**：待复核的 Room 贴列表（模型判定为边界 / 低置信的那部分）。每条显示：贴全文、发布者、**模型初筛结果**（判定 pass/borderline/violate、置信度、命中的版规条目）。
2. 操作三件套：**通过 / 拒绝（选模板理由）/ 改类型后通过**。所有操作留审计痕迹（界面上显示"由谁在何时操作"即可）。
3. 简单指标页：待审数量、今日处理量、自动通过 / 自动拒绝 / 人工三分支的比例。

**数据契约**：贴与审核元数据（room_posts 全字段 + moderation 里的模型判定 / 置信度 / 规则命中 + reviewed_by）。

**关键交互**：键盘快操作友好（队列逐条处理）；拒绝理由从版规模板中选，可微调。

**空态与错误态**：队列清空 → "没有待审项"；操作冲突（已被处理）→ 刷新提示。

**对应验收**：§10-7 后半（人工队列可操作）。

## 14. 需要设计侧回答的开放问题

1. **整体视觉方向**：Atlas 是"系统"人格——偏终端 / HUD / 克制的深色系统感，还是校园产品的明亮友好感？两者张力很大，需要先出 2 个方向的 moodboard 拍板。现有 system UI（XP / 等级组件）已有一版视觉，新方向需要决定是延展它还是隔离它。
2. **Block 日历密度**：时间轴最小粒度（15min？30min？）；单日超过 ~12 个块时的折叠 / 压缩策略；通勤块（常见 20–40min）在高密度日如何不糊成一团；周视图在 1280px 宽度下 7 列的最小可读块宽。
3. **移动端断点**：Web 先行但学生大量用手机浏览器。至少定义：≥1024（桌面双栏？）、768–1024、≤480 三档；周视图在手机上是横滚 7 列还是退化为 3 日视图？拖动重排在触屏上的交互方案（长按拖 vs 编辑模式）？
4. **界面语言**：用户是 Rutgers 学生，产品界面应为英文——Atlas 语气规范的英文版基调（本文规则如何translate：no exclamation marks 直接成立，"主线在等一步"的英文句式需定稿）。
5. **状态色系**：块的六种状态 + watch 的三种状态 + 请求的四种状态，共用一套语义色还是分域？shed（已卸载）与 missed（已错过）必须可区分且都不能像"错误"。
6. **Atlas 消息容器**：inbox 消息、块内 reason、保护模式横幅、空档推送卡是同一容器语言的四种尺寸，还是不同组件？暗色 / 亮色两个主题是否都要（建议 MVP 只做一个）。
7. **分享卡（W8 后增量，仅预研）**：小票风完成回执（"MONDAY RECEIPT: 6 blocks planned, 5 executed"）的视觉预留——不进 MVP，但主视觉方向定稿时请确认它能长出来。
